# Как контрибьютить

Спасибо, что заглянул. Это headless-мост, который заменяет qTox и зеркалит
личную Tox-переписку в Telegram. Проект маленький и обозримый, так что
разобраться и прислать правку - дело часа, а не недели. Ниже всё, что нужно
знать, чтобы поднять окружение, прогнать тесты и оформить PR так, чтобы его
было приятно мержить.

Если что-то в этом гайде устарело или не сходится с кодом - это само по себе
повод завести issue или PR.

## С чего начать

1. Заведи issue, если хочешь обсудить идею или баг до того, как писать код.
   Для мелких фиксов (опечатка, очевидная ошибка) можно сразу PR.
2. Форкни репозиторий и работай в отдельной ветке - в `main` напрямую не
   коммить.
3. Прежде чем пилить новое - загляни в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md),
   там видно, как устроен проект и что пока не сделано.

## Окружение для разработки

Нужен Python 3.12 (поддерживается до 3.15) и [`uv`](https://github.com/astral-sh/uv).
Системный `libtoxcore` для разработки **не нужен** - ядро тестируется без него.

```bash
uv venv
uv pip install -e ".[dev]"
```

Это создаст `.venv/` и поставит пакет в editable-режиме вместе с dev-зависимостями
(pytest, pytest-asyncio, pytest-cov).

Расклад по слоям проекта:

- `config`, `store`, `router`, `file_transfer`, плюс адаптеры - чистый Python,
  тестируются и запускаются локально без нативных зависимостей.
- `tox_service` обёрнут так, что нативная биндинг-часть нужна только в реальном
  запуске; юнит-тесты работают на заглушках.
- `app`, `__main__`, `nodes` завязаны на живую сеть и сборку - их проверяем не
  юнит-тестами, а через `docker build` и запуск (см. ниже).

## Тесты и покрытие

Гоняем pytest с покрытием:

```bash
.venv/bin/python -m pytest -q --cov=bridge
```

Чего ждём от PR:

- Тесты зелёные.
- Покрытие держим на уровне **80%+**. Новый код приходит со своими тестами -
  это не формальность, а способ не словить регресс в мосте, который работает
  без присмотра.
- Тесты пишем по TDD, когда это уместно: сначала падающий тест, потом
  реализация.

Удобный отчёт по непокрытым строкам:

```bash
.venv/bin/python -m pytest -q --cov=bridge --cov-report=term-missing
```

### Что исключено из покрытия и почему

`src/bridge/app.py`, `src/bridge/__main__.py` и `src/bridge/nodes.py` намеренно
вынесены из coverage (`[tool.coverage.run] omit` в `pyproject.toml`). Это
точки, завязанные на реальную сеть и сборку нативной части: оркестрация
процесса, точка входа, bootstrap-ноды Tox. Юнит-тестами их гонять смысла нет -
они проверяются интеграционно, живым запуском. Не пытайся искусственно
накручивать на них покрытие.

### Нативная часть (libtoxcore + py-toxcore-c)

Биндинг к Tox строится из исходников и требует системного `libtoxcore`. Локально
его ставить не обязательно. Если правка задевает нативный слой (`tox_service`,
сборку, версии Tox) - проверяй через Docker:

```bash
docker build -t qtox-bridge .
```

Сборка тянет и компилирует `c-toxcore` (TokTok) и `py-toxcore-c`, поэтому
первый прогон занимает несколько минут. Если меняешь `Dockerfile` или
`docker/pytox-setup.py` - обязательно прогони `docker build` и убедись, что
образ собирается, прежде чем слать PR.

## Стиль кода

- **PEP 8** - базовая планка.
- **Type hints** на публичных функциях и методах. Мост асинхронный, типы сильно
  экономят нервы при чтении.
- Форматирование и линт - `black` и `ruff`. В проект они пока не зашиты как
  зависимость, так что ставь их себе глобально (`uv tool install ruff black`)
  или в venv и прогоняй перед коммитом:

  ```bash
  ruff check src tests
  black src tests
  ```

  Дефолтные настройки black и ruff нас устраивают; экзотических правил не
  вводим. Если ruff ругается по делу - чини код, а не глушит правило.
- Много маленьких файлов лучше одного большого. Ориентир: модуль до ~400 строк,
  функция до ~50. Организуем по смыслу (feature/domain), а не по типу файла.
- Ошибки обрабатываем явно, молча не глотаем. Внешние данные (Telegram, Tox,
  конфиг, файлы) валидируем на границе.
- Без хардкода - параметры идут через переменные окружения, см. `.env.example`.
- Секреты, токены, профили (`*.tox`), `.env` и `data/` в репозиторий не
  попадают (они в `.gitignore`) - проверь diff перед коммитом.

## Формат коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/):

```
<тип>: <короткое описание в нижнем регистре, без точки в конце>

<необязательное тело: что и зачем, не "как" - это видно в diff>
```

Типы:

| Тип        | Когда                                              |
|------------|----------------------------------------------------|
| `feat`     | новая функциональность                             |
| `fix`      | исправление бага                                   |
| `docs`     | только документация                                |
| `test`     | только тесты                                       |
| `refactor` | переработка без изменения поведения                |
| `perf`     | оптимизация производительности                     |
| `chore`    | рутина: зависимости, конфиги, служебное            |
| `ci`       | сборка и CI                                        |

Примеры:

```
feat: пересылка файлов из топика обратно в Tox
fix: дедуп больше не теряет сообщения при переподключении
docs: уточнить требование Threaded Mode у бота
```

Один коммит - одно осмысленное изменение. История должна читаться.

## Pull request

1. Ветка от свежего `main`, осмысленное имя (`feat/file-relay`, `fix/dedup`).
2. Перед отправкой прогони локально:
   - `.venv/bin/python -m pytest -q --cov=bridge` - зелёные тесты, покрытие 80%+;
   - `ruff check` и `black` - чисто;
   - `docker build .` - если трогал нативную часть или Dockerfile.
3. В описании PR опиши: **что** меняется, **зачем**, и **как проверял**.
   Если есть связанный issue - сошлись на него.
4. Держи PR сфокусированным. Несвязанные правки разноси по отдельным PR - так
   их быстрее ревьюят.
5. На комментарии ревью отвечай правками в той же ветке; force-push без нужды
   не делай.
